# RB-029 — Patient.medicalHistory encryption inventory and migration design

- **Audit base:** `main` at `6581695e91eb70c638bc0b94efb10773d8882dd9` (2026-10-25). The original inventory observations below describe that revision; newer code must be assessed from its current source.
- **Release blocker:** RB-029, P0, PHI / clinical data protection.
- **Status:** static source inventory and staged rollout design exist; the versioned JSON envelope codec, compatibility decoding, guarded backfill utility, canonical CRM writers and odontogram writer were subsequently implemented and merged. The remaining consumers, concurrency behavior, staging dry run, backup/rollback and exact-head release gates are still open.
- **Safety boundary:** this document describes source paths and a safe rollout. It does not change schema, encrypt production data, run a backfill or infer anything about the deployed database provider.

## Implementation reconciliation — 2026-10-26

- Current main (`ac913cc3389a294d0b135a852b035ddddb1018ca`) includes the versioned `__dentvisionEncryptedV1` envelope codec in `dentvision-backend/src/lib/phi.ts`; canonical Patient CRUD and odontogram write paths use `encryptMedicalHistory`, and relevant readers decode the envelope before returning clinical data.
- Follow-up review found the Patient Portal profile writer still used `encryptField(String(body.medicalHistory))`, which destroys structured JSON shape; the candidate switches to the shared codec. Additional review found that canonical Patient create/upsert and PATCH boundaries need to reject caller-provided root ciphertext/envelope markers because the codec deliberately supports idempotent internal envelope round-trips. Code commit `2368ff723efd5ea02349fd39dfec47c6ff87360e` on the candidate branch guards all three API writers with `isClientSuppliedEncryptedMedicalHistory`; this prevents replay of untrusted ciphertext from being treated as service-produced data. Route/codec regression tests are added, but exact-head CI is still pending.
- The candidate adds a focused source-contract regression test. The shared codec now also fails closed when a root-level `__dentvisionEncryptedV1` marker is present but its value is malformed or not `ENC:` ciphertext, instead of treating that object as legacy plaintext JSON. Exact-head CI is still pending. No production/staging database operation or backfill has been executed.

## Executive finding

`Patient.medicalHistory` is `Json?` in `dentvision-backend/prisma/schema.prisma` (Patient model around line 427) and is created as PostgreSQL `JSONB` in `dentvision-backend/prisma/migrations/init_full_schema/migration.sql` (around line 175). The normal CRM stores a structured object. The field-encryption helper in `dentvision-backend/src/lib/phi.ts` only encrypts/decrypts `medicalHistory` when its runtime value is a **string**, not a JSON object. The patient create and patch paths write the object directly as `Prisma.InputJsonValue`. No production call to `encryptPatientFields()` was found in the static sweep. Consequently, the JSON object written by normal CRM workflows is not encrypted by this helper and may remain readable in database pages, dumps and backups.

The audit baseline also had a Patient Portal representation mismatch: `PUT /api/patient-portal/me/profile` assigned `encryptField(String(body.medicalHistory))` into the JSON column. An object became `"[object Object]"` before encryption. Candidate `security/rb029-patient-portal-history-envelope-20261026` now passes the submitted value through `encryptMedicalHistory()` so structured JSON is preserved, and rejects already-encrypted `ENC:` strings / reserved envelope objects from clients. This is a candidate fix, not yet merged or release-verified.

A field-level encryption change must therefore be an application-wide data-contract change, not an isolated utility edit.

## Method and coverage

The audit used source inspection on the exact `main` SHA shown above:

- `medicalHistory` appears explicitly in **58 text matches across 23 files** under frontend, backend, Prisma migrations/schema, tests and docs.
- A wider sweep found **85 textual `prisma.patient` ORM-call lines across 33 backend paths**, including test files. The wider count is not a count of unique API endpoints: some lines contain multiple operations, and many use a restricted `select` only for identity or authorization. These paths must be rechecked for implicit whole-row serialization in implementation review.
- No explicit Prisma JSON-path filter against `medicalHistory` was found in the searched source set. The CRM does read/modify/write the `teeth` sub-object, so JSON object behavior is still a hard compatibility requirement.
- No production database query, dump, backup or migration was run as part of this source-only inventory; actual row-type counts and legacy formats are unknown until an isolated, read-only dry run is approved.

## Current cryptography and tests

- `dentvision-backend/src/lib/fieldEncryption.ts` currently uses AES-256-GCM, a random 16-byte IV and 16-byte authentication tag. The raw format is `iv:tag:ciphertext`; the key is derived from `ENCRYPTION_KEY` using `scryptSync` with a fixed salt. Production throws when the key is absent/too short.
- `dentvision-backend/src/lib/phi.ts` prefixes encrypted strings with `ENC:` and allows unmarked strings through for backwards compatibility. Its `encryptPatientFields()` and `decryptPatientFields()` branches check `typeof medicalHistory === 'string'`, so they do not process the object currently used by CRM. No `encryptPatientFields()` production call site was found in the sweep.
- The existing `phi.test.ts` production-failure test supplies a **string** history. It does not prove JSON-object encryption. `teethStore.test.ts`, `cross-clinic.service.test.ts` and `clinical-core.spec.ts` currently exercise object-shaped history, not encrypted envelopes.
- The current format has no field-level ciphertext version or key ID; the helper has no explicit keyring/rotation migration contract.

## Original implementation contract — remaining acceptance checklist

The checklist below predates the shared V1 codec and compatible writers/readers. Treat it as a release-closure checklist, not as a statement that the implementation is absent. The shared codec and some call sites exist; a single typed repository boundary, all-consumer verification, explicit key metadata/rotation, concurrency protection, derivative-PHI controls, staged dry run and rollback evidence remain open unless separately verified.

1. **One codec and one repository boundary.** Introduce a typed `MedicalHistory` codec/repository used by all Patient create/update/read paths. Its public read result is a validated structured object (or `null`); its write method accepts only the validated object. Do not allow route/UI modules to encode/decode ciphertext themselves or spread arbitrary Prisma JSON into the UI.
2. **Versioned encrypted representation.** Persist a tagged envelope with an explicit format version, algorithm and key ID, e.g. `{$format: 'dentvision.phi.medicalHistory', v: 1, alg: 'A256GCM', kid: 'phi-2026-01', ciphertext: '...'}`. Ciphertext must be authenticated with a unique IV per write. Store the envelope in the JSONB field only after all readers/writers use the codec; do not pass the envelope to Prisma-facing reports, the AI model, or frontend state. A separate ciphertext column is an alternative only if the migration plan includes a strict deadline to clear the old plaintext column—keeping both populated would not close the at-rest blocker.
3. **No silent fallback.** Production writes must fail closed if encryption is unavailable. Decryption of a recognized envelope with a missing/unknown key, bad authentication tag, invalid JSON, or unsupported version must fail closed and emit a redacted operational error. Do not interpret ciphertext as an empty history or silently revert to plaintext. Legacy plaintext-object support is temporary and read-only during migration; it must be measurable and removable.
4. **Atomic read/modify/write.** `PATCH`, `teethStore.syncTeeth()` and `applyToothFindings()` must decrypt, validate, merge and re-encrypt without dropping unrelated fields. Use a transaction/optimistic-concurrency predicate based on the row version/`updatedAt`; retry or return a conflict rather than overwriting a concurrent edit.
5. **Keep tenant/branch and consent gates before decryption.** Centralize crypto after authorization has resolved the allowed clinic/organization. Cross-clinic reads still require a live approved grant and preserve the audit log. Patient Portal reads remain self-bound and consent-gated. Decryption itself is not an authorization decision.
6. **Account for derivative PHI.** Decide and test a retention/access policy for complaint text in `ai_events.payload` and clinical details echoed in `ai_messages.content` / `ai_sessions.messages`. A source-column encryption pass cannot remove or encrypt these derived copies. Review backups/exports and relevant data-retention behavior before declaring overall clinical-data protection complete.

## Migration / backfill runbook — do not execute until all path changes and approvals are complete

1. **Read-only dry run in an isolated database.** Count `NULL`, JSON object, JSON array, JSON string, number/boolean and malformed legacy values using `jsonb_typeof`; identify `ENC:`-marked string values separately. Do not print record payloads or clinical values. Record only counts, a time-bound snapshot ID, and non-reversible row identifiers/hashes for exceptions. Verify a tested backup/restore and key availability before any production-sized run.
2. **Deploy compatibility readers and encrypted writers first.** New writes are encrypted/versioned; reads understand both the old object and the versioned envelope. Do not continue dual-writing plaintext. Patient Portal's object/string contract must be fixed here, along with CRM list/detail, odontology, AI, cross-clinic and events.
3. **Batch backfill by stable keyset cursor.** For each eligible row, parse the legacy object, validate its root shape, encode/encrypt it, then conditionally update only if the source value/version still matches what was read. Keep each batch bounded and transactional; use checkpoints so a restart resumes, and make repeated runs idempotent. Concurrent app updates must win over stale backfill work.
4. **Exception handling without PHI.** Unknown legacy types, malformed JSON strings, bad `ENC:` values and crypto errors go to an exception ledger containing patient ID or keyed hash, reason code and timestamps—never the plaintext payload. Do not silently skip them and call the migration successful; quantify them and stop/rollback as specified in the runbook.
5. **Reconcile and verify.** Compare pre/post row counts, NULL counts and representation counts; verify no eligible plaintext object/string rows remain; round-trip a stratified sample in a protected test harness and compare a one-way checksum of canonical JSON (never log the canonical history); run patient/portal/odontogram/cross-clinic/AI integration suites with tenant/branch assertions. Scan candidate API responses to ensure no envelope is exposed.
6. **Close legacy mode and review backups.** Only remove legacy read support after the exception count is zero or formally dispositioned, exact production evidence is reviewed, and rollback/restore has been rehearsed. The migration does not scrub older backups; follow the configured backup-retention lifecycle and access controls, and document the date when plaintext backups have expired.

## Required test matrix before RB-029 can close

- Codec tests: structured nested JSON, Unicode, null, deterministic schema validation, no known plaintext marker in the persisted envelope, randomized ciphertext per write, version/key ID, key rotation, missing/unknown key, invalid tag, unsupported version, malformed JSON and production fail-closed behavior.
- Round-trip API tests: POST/list/detail/summary/PATCH, MedicalCard upsert, Patient Portal GET/PUT with an object payload, `syncTeeth`, `applyToothFindings`, and same-tenant parallel updates preserve all unrelated history fields.
- Downstream tests: authorized AI `getPatientCard` receives decoded data and no envelope; cross-clinic `getHistory` works only with an active grant and records access; AI event payload/AI transcript PHI policy is enforced; reports and generic exports do not expose ciphertext envelopes or old plaintext values unexpectedly.
- Security tests: clinic/branch/organization IDOR denial before decryption, patient-self binding/consent, unauthorized roles, tenant isolation, Sentry/localStorage redaction still passes, and decrypt errors do not return partial records.
- Backfill tests: dry-run causes zero writes; batch resume after interruption; idempotent second pass; concurrent update conflict; malformed value accounting; exact before/after counts; no PHI in console or exception ledger; rollback/restore drill.

## Remaining boundaries

This inventory does **not** establish that every separate Patient field is encrypted. `phone`, `email`, `address`, `notes`, IIN blind index/search behavior, images/documents/storage URLs, visit and treatment-plan fields, AI messages/events and backup copies have their own privacy/data-retention properties. They require their own explicit decisions. RB-029 remains **OPEN / P0** until the codec, all compatible consumers, audited backfill, key operations and exact production evidence are complete.
