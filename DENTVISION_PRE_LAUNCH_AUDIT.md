## 1. Executive Summary

DentVision — мультитенантная SaaS-платформа для стоматологических клиник: CRM (пациенты/записи/лечение/касса), диагностический маркетплейс (направления в центры КТ/лаборатории), товарный маркетплейс, академия (курсы), ИИ-ассистент (Jarvis) поверх всего перечисленного, аналитика/BI, консоли суперадмина.

За этот аудит: **полная разведка** (три параллельных агента — межтенантная изоляция/IDOR, финансовая атомарность, RBAC+ИИ+файлы — плюс отдельный обход фронтенда), **девять находок уровня P0/P1 исправлены и верифицированы** (включая два — обход авторизации на назначении ролей и полностью нерабочее хранилище файлов — которые по отдельности были бы блокерами запуска), **два дополнительных P2-фикса** найдены и закрыты по ходу верификации (сломанный сид демо-центров диагностики; отсутствие индикации ошибки на кассе). Полный список — §21–23.

**Что не подтверждено фактически** (см. NOT VERIFIED в соответствующих разделах, это не «не проверялось никогда», а «в этой среде физически не проверить»): реальные Kaspi/AWS-креды в проде, экран согласия Google OAuth, полный e2e-проход глазами человека в браузере по всем 15 шагам из задания, мобильная вёрстка на реальных брейкпоинтах, нагрузочное поведение, актуальность i18n по трём языкам, состояние бэкапов БД.

## 3. Security Audit

### 3.1 Найдено и исправлено в этом аудите

- **P0-1 — обход авторизации на назначении ролей** (privilege escalation). `POST/DELETE /api/iam/persons/:id/roles` не проверял ничего, кроме факта входа — любой пользователь мог назначить себе роль владельца в чужой организации. Исправлено, 9 тестов, живой прогон через реальную сюиту. Подробности — §21.
- **P0-4 — фиктивная транзакция миграций.** `runOnceMigration` не передавал `tx`-клиент в тело миграции, сырой SQL шёл мимо транзакции — частичный сбой не откатывался. Исправлено и **дважды подтверждено живьём** на реальном Postgres (воспроизведён баг на старом коде, подтверждён откат на новом).
- Секретов в репозитории не найдено (grep по `sk-`/`AKIA`-паттернам и `.env`-файлам — чисто, VERIFIED).
- `helmet` подключён, CORS настроен по allowlist (не wildcard), 5 независимых `rate-limit`-лимитеров (общий/auth/AI/guest/webhook) — прочитано в `app.ts`, VERIFIED.
- Глобальный `errorHandler` не отдаёт stack trace клиенту — только `'Внутренняя ошибка сервера'`, стек только в `console.error` (VERIFIED, см. §17).

### 3.2 Найдено, не исправлено (не P0/P1, задокументировано)

- **~89 мест в бэкенде** возвращают клиенту `err.message` из общего `catch` вместо безопасного сообщения (паттерн `error: err.message`/`error: e.message`). Часть из них — намеренно понятные бизнес-ошибки («Пациент не найден»), но для непойманных исключений (например, `PrismaClientKnownRequestError`) это может отдать в ответе технические детали (имена таблиц/колонок). Не блокер (глобальный `errorHandler` — страховка от самого страшного случая, необработанных исключений), но системный паттерн, который стоит привести к одному правилу в отдельном заходе — 89 точек правки это не "P2, безопасно и очевидно" объём для одного прохода.
- **`middleware/rbac.ts`** — DB-права аддитивны к легаси ролевой матрице (если DB-проверка не проходит, откатывается на legacy-матрицу вместо отказа). Не эксплойт сам по себе (сегодня legacy-матрица и есть основной источник истины), но означает, что DB не может *сузить* доступ — только расширить. Архитектурный долг, часть более крупного IAM-рефакторинга (см. §24), не блокер.

## 4. Authentication & Authorization

- Регистрация/вход по email+паролю, вход через Google (ID-token flow, `google-auth-library`, аудитория/issuer/exp проверяются библиотекой) — код прочитан целиком в предыдущей фазе этой же сессии, юнит-тесты на верификатор были зелёными.
- **Живой прогон в этом аудите**: `POST /api/auth/register` на поднятом с нуля сервере против чистого Postgres — вернул `200`, валидный access/refresh JWT, роль `STUDENT` (дефолт для саморегистрации без клиники — подтверждено намеренным, см. §21 P1-5). **VERIFIED**.
- JWT: access+refresh, оба со сроком жизни из `JWT_EXPIRES_IN`/`JWT_REFRESH_EXPIRES_IN` (24h/7d по умолчанию), сессии — отдельная таблица в БД (не просто безсостояние JWT), значит **отзыв сессии реален** (не просто "токен ещё не истёк"). VERIFIED по коду.
- Сброс пароля: письмо реально отправляется (SMTP, env-gated), успешный сброс гасит все сессии, попытка с истёкшим токеном — не гасит (это было отдельно исправлено раньше в этой же серии работ, до начала текущего аудита — не перепроверялось заново в этом заходе, NOT RE-VERIFIED в этом конкретном проходе, но было VERIFIED в момент фикса).
- **P0-1 закрывает** конкретный сценарий эскалации через смену роли по API — единственный найденный в этом аудите путь, где пользователь мог реально дать себе больше прав, чем должен.
- Не проверено в этом заходе: brute-force защита сверх общего rate-limit'а (есть отдельный `authLimiter`, содержимое лимита не пересчитывалось); поведение при одновременных сессиях с разных устройств (логика на месте — отдельная таблица сессий — но многодевайсный сценарий не прогонялся живьём). **NOT VERIFIED**.

- P1-1 — легаси AI-фоллбэк (`doctor.agent.ts`) искал пациента по `id` без проверки `clinicId` — межклиничная утечка медкарты/КТ/создания плана лечения в окне, когда работает не основной оркестратор, а старый intent-роутер. Исправлено.

**Найдено, не исправлено (низкий риск, задокументировано):**

**Перепроверены заявления стороннего черновика** (T-2/T-3/T-4/R-1 из предсуществовавшего файла):

Отсутствие типов — само по себе технический долг (см. §24), не подтверждённая уязвимость.

## 6. Database

- PostgreSQL, Prisma ORM, схема прочитана целиком.
- **P0-4** (фиктивная транзакция стартовых DDL-миграций) — исправлено, **дважды живьём проверено** на реальном Postgres 16: воспроизведён баг на старом коде (таблица оставалась после сбоя середины блока), подтверждён откат после фикса.
- **Отдельная находка того же класса, не исправлена**: ручной блок `marketplace_iam_finance` (`index.ts:274+`) — не идёт через `runOnceMigration`, смешивает `CREATE TABLE IF NOT EXISTS` (сами по себе идемпотентны) с bulk-сидом каталога через обычные `prisma.*`-вызовы вне какой-либо транзакции. Технически та же уязвимость к частичному применению, но каждый отдельный `CREATE TABLE IF NOT EXISTS` в нём безопасен для повтора — частичный сбой не катастрофичен так, как было бы с `ALTER TABLE`. Не тронут в этом заходе — рефактор большого смешанного блока рискованнее, чем оправдано без отдельного запроса; см. §24.
- **P2 (найдено и исправлено по ходу верификации)**: сид демо-центров диагностики/лабораторий передавал поле `description`, которого нет ни у `DiagnosticCenter`, ни у `Laboratory` в схеме — сид **всегда** падал (non-fatal catch маскировал это). Живьём подтверждено: на старом коде — 0 центров создано на чистой БД; на исправленном — 4 центра + 2 лаборатории созданы корректно.
- **Формальная папка миграций Prisma не воспроизводится с нуля** — `prisma migrate deploy` на пустой БД падает на `20260808_add_performance_indexes` (`relation "invoices" does not exist»`), потому что реальный прод полагается на комбинацию базовой миграции + рантайм-DDL в `index.ts`, а не на чистое воспроизведение всей папки миграций. Это pre-existing состояние (не внесено этим аудитом), обнаружено при попытке живого boot-теста — итоговый воркэраунд (`prisma db push` вместо `migrate deploy` на тестовой БД) сработал и позволил провести полную живую проверку, но сам разрыв (`migrate deploy` не воспроизводит схему с нуля) остаётся нерешённым и является риском для дизастер-рекавери (создание новой БД с нуля в аварийной ситуации не сработает тем же путём, что обычный деплой). **Зафиксировано как находка**, не в scope этого захода чинить (структурная проблема миграционной истории, не изолированный баг).
- Атомарность денежных операций — см. §13 (Finance).
- Race conditions на складе (маркетплейс) — атомарный `updateMany` с guard'ом на `stock: {gte: qty}` внутри транзакции, подтверждено чтением кода (VERIFIED по коду, не нагрузочным тестом на конкурентность).

## 7. API

- REST, Express, все защищённые роуты за `authenticate` + (где нужно) `requirePermission`/явные resolver'ы.
- Идемпотентность платежей: `Idempotency-Key` теперь **обязателен по факту** — при отсутствии заголовка сервер детерминированно выводит ключ (`sha256(userId:body)`), так что повторный клик коллапсирует в одну и ту же запись `IdempotencyRecord` (уникальный индекс в БД). Подтверждено чтением кода (это фикс предыдущей, не этой сессии — перепроверено как всё ещё в силе).
- Webhook-replay safety: все три пути «оплата→paid» (`/:id/confirm`, `/callbacks/kaspi`, `/callbacks/kaspi/clinic/:clinicId`) коротят выполнение, если платёж уже `paid` — подтверждено чтением всех трёх.
- **P1-2** — клиничный Kaspi-webhook не был обёрнут в транзакцию (в отличие от двух других путей) — исправлено, приведено к паритету.
- Цена/сумма всегда пересчитывается на сервере, клиентское значение отбрасывается (`shop.routes.ts`, `void total`) — подтверждено чтением кода.
- SQL-инъекции: весь сырой SQL идёт через `$executeRawUnsafe`/`$queryRawUnsafe` с параметризацией (`$1, $2...`), не через конкатенацию строк — выборочно перепроверено в местах, тронутых P0-4 фиксом, инъекций не найдено. Полный аудит каждого из ~95 сырых SQL-вызовов в `index.ts` не проводился — **NOT VERIFIED** для всего файла целиком, только для затронутых фиксом блоков.
- Rate limiting — см. §3.

## 9. Diagnostic

- Поток: клиника → направление → центр/лаборатория → анализ → результат → подпись → возврат в карту пациента. Изоляция входа в кабинет центра/лаборатории — двумя путями (модерируемая заявка + инвайт-код), сделано в предыдущей фазе этой же серии работ (PR #187), не перепроверялось заново в этом конкретном заходе.
- **P0-4-побочный, но прямо относящийся находка**: сид демо-центров/лабораторий был **полностью нерабочим** на любом свежем деплое (см. §6) — то есть до этого фикса ни одна свежая клиника физически не могла отправить направление куда-либо (список центров был бы пуст). Исправлено и подтверждено живьём.
- Комиссия платформы считается на сервере (`platformFee`), не с клиента — подтверждено чтением кода в предыдущей фазе, не перепроверялось заново.

- Живой e2e-прогон полного диагностического цикла (направление → приём → результат → возврат в карту, глазами человека, в браузере) — **NOT VERIFIED** в этом заходе.

## 10. AI

## 18. File Upload & Medical Data

Самая крупная находка всего аудита.

- **P0-2 — файловое хранилище было полностью нерабочим.** `multer.memoryStorage()` без реальной записи куда-либо; `S3_ENDPOINT/S3_BUCKET/S3_ACCESS_KEY/S3_SECRET_KEY` были объявлены в конфиге, но нигде не использовались; в БД сохранялся фиктивный URL `/mock-storage/...`, который не обслуживал ни один роут. **Каждый загруженный рентген/КТ/документ-согласие бесследно исчезал.** Для медицинского продукта это блокер сам по себе, независимо от денег.

  **Фикс:** реальное S3-совместимое хранилище (`@aws-sdk/client-s3`), подписанные (presigned, TTL 5 мин) ссылки на скачивание вместо публичных URL, загрузка без настроенных креденшелов теперь отвечает `503` вместо фейкового успеха. Лимит размера поднят с 10MB до 60MB (реальные CBCT/DICOM обычно 50MB+).

  **Живая верификация**: поднят локальный S3-протокольный сервер (`s3rver`), полный цикл загрузка→ключ хранилища→подписанная ссылка→скачивание→побайтовое сравнение содержимого — совпадение подтверждено. **Реальный AWS S3 с реальными кредами — NOT VERIFIED**, недоступен в этой среде.

- Контроль доступа к файлам — `assertSameClinic` на всех точках чтения (`GET /:id`, `GET /:id/content`), подтверждено уже существовавшим кодом, не тронуто фиксом (presigned URL генерируется **после** этой проверки, не вместо неё).
- Валидация типа файла — только по расширению (allowlist), не по magic bytes. Пока хранилище было нерабочим, это было неактуально; теперь, когда файлы реально сохраняются, это осталось некритичной, но реальной находкой (P3) — переименованный вредоносный файл с разрешённым расширением пройдёт фильтр. Не исправлено в этом заходе.
- PHI в логах/URL/ошибках — точечно проверено (§3), в консольных логах бэкенда не найдено ни ФИО, ни ИИН, ни диагнозов, только счётчики и статусы.

## 25. Launch Blockers

**На момент начала этого аудита были 4 блокера (P0-1..P0-4) — все закрыты.** На текущий момент (конец аудита) **блокеров, найденных и подтверждённых в этом заходе, не осталось.**

Единственная оговорка снимающая уверенность до "полной": **P0-3 закрыт только на уровне документации `render.yaml`** — фактическое наличие рабочих `KASPI_MERCHANT_ID`/`KASPI_API_KEY` в самом Render dashboard **не проверено и не может быть проверено из этой среды**. Если эти значения не заданы в реальном проде — платежи (подписки/маркетплейс/диагностика/академия) будут выглядеть рабочими, но не проводить реальных денег. Это не находка нового бага, а прямое следствие уже задокументированного P0-3 — просто его нельзя закрыть полностью без доступа к продовой панели Render, которым я не располагаю.

## 26. Final Release Decision

# 🟡 READY WITH KNOWN RISKS

**Обоснование.** Все найденные в этом заходе блокеры (P0-1..P0-4) закрыты, верифицированы кодом, тестами и (где физически возможно) живыми прогонами против реального Postgres и S3-совместимого сервера. Ни одна из оставшихся находок (§23) не создаёт прямого пути к потере денег, утечке медданных или обходу доступа — они либо архитектурный долг, либо UX-огрехи, либо структурные риски, требующие отдельного, более крупного захода, не разумного в рамках одного аудита.

**Условие для перехода в 🟢**: подтверждение человеком (не мной, не из этой среды) трёх вещей, которые физически не проверить без доступа к продовой инфраструктуре — (1) реальные `KASPI_MERCHANT_ID`/`KASPI_API_KEY` заданы в Render и хотя бы один реальный платёж прошёл сквозной цикл; (2) реальные `S3_BUCKET`/`S3_ACCESS_KEY`/`S3_SECRET_KEY` заданы и хотя бы один реальный файл загружен/скачан через прод; (3) хотя бы один живой e2e-проход человеком по основным путям (регистрация → клиника → пациент → запись → оплата) в реальном браузере на проде, а не в этой среде.

**Условие для перехода в 🔴**: только если при попытке (1)/(2) выше выяснится, что учётные данные отсутствуют или платежи/файлы реально не работают в проде — тогда P0-3/P0-2 возвращаются в статус блокера до устранения на инфраструктурном уровне.
